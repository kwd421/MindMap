# Track X v0.2 — Independently Authored Raw-Passage Protocol

**Status:** protocol and development implementation phase; held-out passages not yet supplied  
**Base:** PR #38 / `track-x-v0.1-manifest-2`  
**Branch:** `research/track-x-v0.2-independent-raw`  
**Coordination:** Issue #7

## 1. Research question

Track X v0.1 proved only that an information firewall and treatment pipeline can work when raw text is an invertible template encoding of the gold event.

Track X v0.2 asks:

> After the parser and verifier policy are frozen on Session-B-authored development passages, can they improve downstream safety and selective accuracy on Session-A-authored held-out passages whose wording and ambiguity were not visible during implementation?

The experiment remains synthetic and topology-scoped, but the raw passages are no longer generated by the same code that parses them.

- optional challenge notes describing intended ambiguity without disclosing answer labels to the verifier.

Session A must not modify the parser, verifier, thresholds, development passages, or evaluation code in the held-out passage commit.

## 3. Freeze sequence

1. Session B commits the protocol, data validator, development passages, parser, verifier, thresholds, tests, and a `FREEZE_V02.json` file containing their hashes.
2. Session B posts a marked `HANDOFF` in Issue #7.
3. Session A writes held-out passages on a child branch from the freeze commit without changing frozen paths.
4. Session A opens a draft PR or posts the branch/head in Issue #7.
5. Session B verifies that only allowed held-out paths changed.
6. The held-out evaluator is run without modifying the frozen parser/verifier or thresholds.
7. Any post-result parser or threshold change creates v0.3 and cannot replace the v0.2 result.

## 5. Passage record schema

Each JSONL record contains only dataset and rendering metadata:

```text
RawPassageRecord(
  passage_id,
  fixture_id,
  topology_family,
  event_id,
  query_id,
  author_session,
  raw_text,
  candidate_condition,
  candidate_mutation,
  raw_available,
  notes
)
```

`candidate_mutation` is an evaluator instruction, not verifier input. The verifier receives the same sanitized `VerifierInput` as v0.1 and cannot access the record, IDs, split, mutation, or query.

Forbidden fields in passage files:

```text
gold_event
expected_answer
answer
recoverable_from_raw
corrected_event
verification_status
confidence
unsafe_disclosure
```

## 6. Passage-writing requirements

Each passage must:

- be written manually rather than emitted by `render_event`;
- preserve enough information for a careful reader to reconstruct the selected event when `raw_available=true`;
- avoid copying the v0.1 template sentence structure;
- contain at least one natural distractor, temporal phrase, pronoun, or reordered field;
- state source identity and relevant world/instance scope when needed for correctness;
- not contain explicit field names such as `about_world_branch_id=` or `policy_operation=`;
- not mention the candidate mutation or answer key;
- remain under the frozen maximum character/token budget.

Held-out passages should vary discourse form across narrative, dialogue, log excerpt, operator note, and indirect report.

## 7. Candidate conditions

For each topology, Session A/B writes at least these records:

1. `clean` — primary candidate matches the canonical event;
2. `field_corruption` — one relevant candidate field is changed;
3. `candidate_omitted` — raw passage survives while the primary candidate is absent;
4. `raw_unavailable` — candidate is corrupted and raw passage is withheld;
5. `ambiguous_raw` — raw passage is present but intentionally insufficient for one material field, so calibrated abstention is correct;
6. `misleading_context` — an irrelevant nearby passage supports the candidate error while the selected raw passage supports the canonical event.

The v0.2 primary endpoint excludes `raw_unavailable` and `ambiguous_raw` from event reconstruction accuracy but includes them in abstention and downstream safety metrics.

## 8. Independent primary and verifier paths

The primary extractor and verifier must not call the same parsing function.

### Primary extractor

- reads the selected raw passage without seeing a candidate;
- produces a `CommonEvent | None` and field confidences;
- may be intentionally lightweight but must be frozen before held-out text exists.

### Verifier

- receives raw passage, primary candidate, context events, and insertion index;
- independently extracts supported fields or detects insufficiency;
- emits `accept | correct | abstain | reject`;
- must not receive primary extractor internal state, parser trace, or candidate-error label.

Shared low-level utilities are limited to Unicode normalization, tokenization, and primitive date parsing. Event-specific regexes or templates may not be shared.

## 9. Correlated-failure conditions

The evaluator includes cases where primary and verifier can fail together:

- the same pronoun is ambiguous for both;
- world branch is implicit and contradicted by a distractor;
- source identity is omitted;
- system time and valid time are both present but syntactically reversed;
- negation or revocation scope crosses a sentence boundary;
- one raw passage is unavailable;
- a misleading adjacent passage repeats the corrupted candidate.

These cases prevent the verifier from being treated as an independent 100%-accurate rescue channel.

## 10. Frozen thresholds and budgets

The following are chosen on development only and recorded in `FREEZE_V02.json`:

- accept threshold;
- correct threshold;
- abstain/reject rule;
- maximum raw characters/tokens;
- maximum parser and verifier calls;
- calibration bins;
- fixed risk/coverage reporting points;
- allowed primary/verifier utility functions;
- dependency versions and commit SHA.

Held-out results are invalid if any threshold or parser rule changes afterward.

## 11. Endpoints

### Primary

Held-out downstream unsafe-use rate at matched non-abstained coverage:

```text
unsafe use = silent wrong answer OR unauthorized disclosure
```

Compare:

```text
primary structured candidate only
primary + independent raw verifier
oracle raw ceiling
```

Generic and typed downstream ledgers receive the same selected event and are expected to agree.

### Secondary

- event exact match and field exact match;
- clean false-correction rate;
- false-accept rate;
- appropriate abstention on ambiguous/raw-unavailable cases;
- correction precision and recall;
- Brier score and ECE;
- risk-coverage curve;
- false denial and unsafe disclosure;
- topology-family macro accuracy;
- raw characters/tokens, calls, corrected fields, and latency/cost;
- generic/typed downstream disagreement count.

## 12. Falsification

The verifier hypothesis is rejected or narrowed if held-out evaluation shows any of:

- no safety improvement at matched coverage;
- excessive clean false correction;
- verifier corrections are often confidently wrong;
- apparent gains rely on fields absent from the raw passage;
- gains vanish on Session-A-authored wording;
- abstention hides most difficult cases without a useful risk/coverage frontier;
- verifier cost dominates the safety benefit;
- downstream G/T receive unequal selected events or diverge materially.
