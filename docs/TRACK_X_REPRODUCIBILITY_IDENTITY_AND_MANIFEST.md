# Track X Reproducibility Identity and Manifest Contract

**Status:** pre-outcome methodological contract  
**Public benchmark hub:** Issue #4  
**Canonical/lifecycle hub:** Issue #7  
**Primary use:** GateMem first; reusable for LoCoMo, LongMemEval, and later public adapters

## 1. Motivation

A benchmark result is not identified by a table of scores alone. The same apparent method name can refer to different:

- upstream benchmark revisions;
- data files or scorer implementations;
- method commits;
- method-visible capabilities;
- checkpoint-state semantics;
- prompts, budgets, dependencies, or seeds;
- opaque identity mappings;
- protected versus publishable artifact bundles.

Conversely, two legitimate reruns can produce different byte hashes solely because evaluator-owned opaque IDs changed while every semantic prediction and official score stayed the same.

This contract separates:

```text
scientific specification identity
execution-replicate identity
byte-level artifact reproducibility
semantic/scorer reproducibility
paired-method comparability
```

---

## 2. Run specification

Let a public benchmark run specification be:

```math
\mathcal{R}=\langle
U,D,E,M,C,Q,\Theta,I,L,N,O
\rangle
```

where:

- `U`: upstream repository and immutable commit/tree;
- `D`: official data-file manifest and hashes;
- `E`: official evaluator/scorer files, hashes, flags, and judge condition;
- `M`: method implementation repository, commit/tree, and dirty state;
- `C`: method-visible capability condition;
- `Q`: checkpoint ordering, grouping, and identity policy;
- `Θ`: method, retrieval, reader, prompt, seed, and budget configuration;
- `I`: checkpoint isolation/compatibility mode;
- `L`: runtime and dependency lock identity;
- `N`: network/filesystem/credential sandbox policy;
- `O`: output artifact allowlist and protected/publishable policy.

The canonical specification digest is:

```math
SpecID=H(CanonicalJSON(\mathcal{R})).
```

Timestamps, temporary directories, runner hostnames, and artifact-upload IDs are descriptive execution metadata and do not enter `SpecID` unless they change a frozen resource or policy.

A changed field in `\mathcal{R}` creates a new specification. It is never silently called a rerun of the old one.

---

## 3. Capability identity is part of the method

The manifest must name the exact capability condition. At minimum for GateMem:

```text
C_raw_directory
  chronological public dialogue prefix
  complete principal identity/display/role directory
  no static relationship/access annotations
  no records, record_refs, or memory_ops

C_relationship_capability
  C_raw_directory plus frozen requester-relevant relationship capability

C_annotated_native_compatibility
  separately enumerated native/annotation capabilities
```

The following also belong to `C` or `Q`, not to informal prose:

```text
source checkpoint ID visible?        yes/no
source as-of turn ID visible?        yes/no
opaque episode ID visible?           yes/no
opaque turn IDs visible?             yes/no
opaque query ID visible?             yes/no
future principal directory visible?  yes/no
record annotations visible?          exact list
```

A score from one capability condition cannot be pooled with another as though only the memory architecture changed.

## 4. Paired run groups

For a paired comparison among methods `A_1,...,A_k`, define a run group:

```math
\mathcal{G}_r=\langle
SpecShared,\{A_1,...,A_k\},K_r,Order_r
\rangle
```

where:

- `SpecShared` freezes all non-method resources and budgets;
- `K_r` is one evaluator-only opaque-ID key for technical replicate `r`;
- `Order_r` is the frozen checkpoint/scenario order.

Every method in replicate `r` receives identical pseudonyms generated by `K_r`:

```text
B0, B1, B2, G-flat, T-normalized, T+raw
  share one run-group key K_r
```

The paired contrast is:

```math
\Delta_r=M(T,K_r)-M(G,K_r).
```

Giving paired methods unrelated keys adds avoidable tokenization and identifier noise. Reusing one key indefinitely across all studies increases memorization and linkage risk.

Use:

```text
same K_r within one paired replicate
fresh independent K_(r+1) across technical replicates
```

Only the key commitment is public:

```math
KeyCommit_r=H(K_r).
```

The key itself must not enter method inputs, prompts, predictions, logs, publishable artifacts, or the repository.

## 5. Three reproducibility tests

### R-A — fixed-key exact replay

Under deterministic methods and a protected escrowed test key, rerun the identical `SpecID` and key.

Require equality of:

```text
checkpoint set and order
normalized scorer-facing predictions
per-checkpoint official deterministic scores
official summary
allowed deterministic audit artifacts
```

Expected equality is byte-level after excluding explicitly nondeterministic timing fields.

This test is protected because publishing the key may weaken the capability firewall.

### R-B — fresh-key semantic noninterference

Rerun the same `SpecID` with a fresh opaque key.

Opaque method/audit identifiers and their containing artifact hashes may change. Require equality of evaluator-normalized semantic outputs and official deterministic metrics:

```math
CanonPred_{K_1}(c)=CanonPred_{K_2}(c)
```

for deterministic methods, where `CanonPred` removes or evaluator-resolves method-side opaque identifiers without changing action or answer content.

At minimum report:

```text
official summaries equal / total
semantic prediction rows equal / total
opaque key commitments changed / total
raw artifact hashes changed where expected
```

### R-C — paired-contrast stability

Across fresh-key technical replicates, report whether the paired method contrast changes materially:

```math
Var_K(\Delta_r).
```

Technical replicates are not independent benchmark samples and do not increase the inferential sample size. They test execution sensitivity.

## 7. Protected and publishable bundles

### Protected bundle

May contain exact benchmark-derived text required for:

```text
scorer-facing predictions
exact prompt context
local leakage evaluation
debugging and adjudication
```

It remains access-controlled and is not automatically uploaded or committed.

### Publishable bundle

Contains only what benchmark terms and the frozen release policy permit:

```text
aggregate and permitted per-item metrics
configuration and hashes
opaque/non-source identifiers where allowed
span coordinates and content hashes
no unnecessary raw excerpts
```

The manifest must truthfully report exposure separately:

```text
raw_text_in_predictions
raw_text_in_protected_audit
raw_text_in_publishable_artifact
prompt_context_text_retained
source_dataset_files_copied
```

A single Boolean such as `raw_benchmark_text_copied=false` is insufficient.

## 8. Atomic output and producer allowlist

An accepted run writes to a new temporary directory, validates the complete artifact set, then atomically finalizes it.

Fail if:

```text
output destination already exists or is non-empty
an expected artifact is missing
an unexpected artifact exists
an artifact producer is not allowlisted
an artifact hash changes after finalization
```

For pinned GateMem deterministic scoring, the expected official scorer outputs are:

```text
predictions.normalized.jsonl
scores.jsonl
summary.json
optional judge_scores.jsonl only under a frozen judge condition
```

Method, outer-evaluator, and official-scorer artifacts remain separate namespaces.

---

## 9. Workflow causality

Outcome jobs must depend on successful source and boundary tests in the same workflow DAG:

```text
source pin/hash gate
  -> ordinary + capability-boundary tests
  -> method execution
  -> exact checkpoint coverage validation
  -> official scorer
  -> artifact/exposure validation
  -> publishable bundle
```

A parallel green workflow does not causally validate an outcome job. A workflow that continues after a failed prerequisite may emit diagnostic artifacts but must set:

```text
official_score_accepted = false
```

and must not update the accepted result manifest.

---

## 10. Moving-upstream and historical reproduction

Two valid study types must be named separately.

### Frozen reproduction

```text
reproduce the existing result at exact upstream/method commits and hashes
```

### Dated refresh

```text
adopt a later upstream commit after a new adapter diff, capability audit,
and amended SpecID
```

Cloning upstream `main` and merely recording its observed head is a dated exploratory refresh, not reproduction of a previously frozen result.

---

## 11. Failure rules

Invalidate the run when any of the following occurs:

1. upstream or method commit is missing, moving, or dirty;
2. paired methods receive different non-preregistered capabilities or opaque mappings;
3. ordinary/boundary tests fail or are skipped;
4. checkpoint IDs are missing, duplicated, or unexpected;
5. source checkpoint order leaks into method capabilities;
6. protected raw-text exposure is falsely declared;
7. official scorer files/flags differ from the frozen specification;
8. output contains stale or unexpected artifacts;
9. method failures are converted into task abstentions;
10. the workflow source commit differs from the recorded producer commit;
11. a result-producing workflow silently commits onto its own source branch without recording both source and result commits;
12. any official/supplemental metric namespace is overwritten or conflated.

Failure artifacts are useful evidence about the pipeline. They are not benchmark outcomes.
